# 预约迁移脚本验收

2026-09-10 在独立 MySQL 8.0.44 实例上完成四条路径，各连续执行两遍仓库原始升级脚本：Core 空库初始化、Core 旧库升级、Commerce 空库初始化、带旧秒杀订单的 Commerce 升级。四条路径共八次脚本执行均成功；结构清单、脚本输出和数据指纹见 [机器可读证据](booking-migrations-2026-09-10.json)。

Core 基准 SQL 自带目标库名，验收仅把 `CREATE DATABASE` 和 `USE` 指向新建的隔离 `_test` 库后初始化。旧库场景移除 GEO 检查约束，使升级实际经过约束补齐及投影表创建路径；14 家种子店铺的数据指纹与 5 个种子用户的数量在两次升级前后保持一致。新增反馈四表正常创建。

Commerce 旧库保留订单 `92001` 与优惠券 `91001`，模拟旧幂等键排序规则和缺失的 Outbox 索引。升级后订单状态、20000 分实付快照、24000 分面值快照及大小写敏感幂等键均不变，库存仍为 7，历史订单补入接单账本且状态为 `ORDER_CREATED`。新增预约与报价共 10 张表、19 个检查约束；脚本的外键、唯一键及关键列形状检查全部通过。直接写入非法预约资源类型和非法反馈来源均被 MySQL 检查约束拒绝，错误码为 3819。

复现入口为 [verify-booking-migrations.ps1](../../tools/migrations/verify-booking-migrations.ps1)。它只连接本地指定端口、创建带唯一运行标识的测试库，拒绝复用已存在的目标库，并保留结果供检查。Windows 使用 Git Bash 执行原始 `.sh` 文件；适配层仅将原生 MySQL 客户端加入 PATH、规范 CRLF 输出并保留退出码。升级脚本新增可选 `CITYCOPILOT_MIGRATIONS_DIR` 以定位迁移文件，容器默认路径不变。

本次没有触碰系统 MySQL80 或 Core/UI 业务库。该证据覆盖受控旧结构与真实 SQL/脚本执行，尚不等同于完整容器发布演练，也不代表所有未知生产结构漂移均能自动修复。
