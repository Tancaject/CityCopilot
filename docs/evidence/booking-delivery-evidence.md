## HTTP 负载和 MQ 故障恢复

[精简负载报告](booking-load-2026-09-10.json)保存正常轮与故障轮的完整阶段统计、数据库不变量、Outbox 快照和运行 JAR 指纹。每轮使用 100 个实际 Core 测试用户、20 个客户端并发，依次执行热门场地、餐厅多人和普通场地各 100 个工作流。商家归属通过真实 Core HTTP 验证，业务请求直接访问单个 Commerce JVM。

正常轮三场景均无非预期失败：热门场地恰好一人取得名额，餐厅按人数分配接待容量，普通场地全部确认。数据库占用未超容量，实际占用等于有效预约 units，总量和当前版本事件一致；没有遗留 HELD。正常轮所有事件均一次发布成功。

故障轮实际停止专用 RocketMQ broker 和 proxy。预约仍正常提交，事件在 Outbox 留存为 FAILED；不确认的 HOLD 在 MQ 停机期间到期并释放占用。恢复后，全部事件通过实际重试变为 PUBLISHED，预约不变量继续成立。预约到期与提醒使用独立调度器，运行线程快照保存在原始结果目录。

该报告提供 HOLD、确认、完整工作流的平均值、p50、p95、p99、最大值，以及工作流吞吐和 HTTP 吞吐。每场景是短时本机负载，不是容量上限或线上 SLA；不能将这些样本写成生产 QPS、线上成功率或转化提升。PUBLISHED 只证明发送端取得发布结果，下游效果见下面单独的消费者闭环证据。

复现命令和边界见[预约负载说明](../testing/booking-load.md)。被 Git 忽略的原始逐请求样本与前后 Prometheus 路径保存在精简 JSON 中；运行脚本可重新生成这些文件。仓库不复制核销凭证、服务令牌、完整环境、线程大文件或服务器日志。

## Commerce JVM 重启与自然到期

[重启验收](booking-restart-2026-09-10.md)及其[机器可读结果](booking-restart-2026-09-10.json)记录了实际停止并重新启动独立 Commerce JVM 的实验。重启使用同一份 JAR 和启动参数，原预约的 HELD 状态、两人占用及持久化截止时间保持不变。没有修改截止时间或调用业务接口触发到期；后台任务自然释放后，首次只读观察在原截止时间后 2522 毫秒看到 HOLD_EXPIRED、占用为 0。该差值包含客户端轮询间隔，不能当作精确任务耗时。

原先 35 秒的 MQ 观察窗口未通过，报告保留该失败记录。后续只读续验确认 HELD 与 HOLD_EXPIRED 两条事件均已发布、进入 Core Inbox 和业务事实，投影为 HOLD_EXPIRED v1；最终正确性验收通过。两条事件从发布到预约消费者处理均约 87 秒，本次没有证明消息实时性能达标，不能据此宣称秒级反馈。这是单机单 JVM 的恢复证据，不代表集群故障切换或生产可用性。

## 空库安装与旧库升级

[迁移验收](booking-migrations-2026-09-10.md)及其[原始摘要](booking-migrations-2026-09-10.json)覆盖 Core 与 Commerce 的空库、受控旧库四条路径，每条连续执行两次仓库升级脚本。旧店铺数据指纹、旧秒杀订单的状态与金额快照、大小写敏感幂等键和库存保持一致；新增表、约束、索引与账本回填通过检查，非法数据由 MySQL 约束拒绝。

复现入口是 [verify-booking-migrations.ps1](../../tools/migrations/verify-booking-migrations.ps1)。这是独立 MySQL 上的真实 SQL 和脚本验证，覆盖的旧结构由测试明确构造，尚不等于完整容器发布演练或所有生产结构漂移的兼容性证明。

## Core HTTP 与真实 MQ 消费闭环

[API 与消息验收](booking-api-acceptance-2026-09-10.md)及其[机器可读结果](booking-api-acceptance-2026-09-10.json)已通过，覆盖 Core 登录与归属边界、实际响应丢失恢复、预算方案查询，以及 Commerce 到 Core 的真实 RocketMQ 消费。

回环代理完整读取已提交的 HELD 响应后断开客户端连接，随后命令查询与同键重试找回同一笔预约，容量只扣减一次；确认与取消后恢复原容量。方案查询的 30 个请求、5 并发均通过响应检查，返回的全部方案满足硬约束，查询没有产生 HOLD。此处延迟来自实际 Core HTTP，单独记录在该 JSON 的 `plans`，不与 Commerce 压测混用。

该预约的 Outbox、Core Inbox 与行为事实事件 ID 集合一致。真实零版本 HELD 晚于确认到达时，仍保留其业务事实，状态投影保持较高版本；确认与取消只各计一次，并关联到 Core 预先签发的本人候选曝光。这里的曝光表示服务端返回过候选，不代表用户实际看过；单个隔离餐厅的闭环也不代表线上成交或转化效果。
